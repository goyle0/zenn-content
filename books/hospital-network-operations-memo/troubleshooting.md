## この章の要点（忙しい人向け）

- 申告は「サービス・経路・端末」に切り分け、**下の階層から**確認する
- 有線は **ping → telnet（ポート）→ traceroute** の3本、無線は **`netsh wlan show interfaces`** が第一手
- 障害の多くは人的ミス。**監視しながら作業し、障害試験は導入時に実施する**
- 障害時は「**直前のトラップ**」を最初に見る

## 「ネットワークがおかしい」と言われたら

利用者からの申告は、ほぼ必ず「ネットワークがおかしい」「電子カルテが遅い」という形で来ます。原因がネットワークにあるとは限らないので、最初にやるのは**3つに切り分ける**ことです。

1. **サービス**（サーバやアプリ）が動いているか
2. **ネットワーク経路**が通っているか
3. **端末**側の問題ではないか

そして、第2章で説明した通り、**下の階層から**確認します。ケーブル → リンクランプ → IPアドレス → ping → ポート → アプリ、の順です。

## 有線の基本4コマンド

| コマンド | 分かること | 注意点 |
|---|---|---|
| `ping` | 相手の機器まで届くか、応答時間はどれくらいか | Windowsは標準設定だとpingに応答しない場合がある（ファイアウォールでICMPが止まる） |
| `nmap` | 相手サーバのどのポート（サービス）が開いているか | 医療機器や本番サーバへの一斉スキャンは、機器によっては動作に影響するので、対象を絞り、事前に関係者へ断る |
| `telnet ホスト ポート` | 相手のサービスまで到達できるか | **Connectedと出ればネットワークの問題ではない** |
| `traceroute` / `tracert` | どの経路を通っているか、どこで止まるか | Linuxの既定はUDPで途中が「\*\*\*」になることがある。`-I` でICMPに変えると通る。Windowsの `tracert` は最初からICMP |

:::message
**tips：「Connectできれば、NW問題ではない」を切り分けの軸にする**
`telnet サーバ 80` の結果は3通りに読み分けます。

- **Connected**：ネットワークは通っている。問題はアプリやサーバ側
- **Connection refused**：サーバまで届いているが、そのポートでサービスが動いていない
- **応答なし（固まる）**：途中のファイアウォールや経路で止められている、またはサーバがダウン

この1コマンドで「ネットワーク担当の仕事か、アプリ担当の仕事か」が決まります。
:::

:::message
**tips：Windowsでの代替コマンド**
Windows 10/11はtelnetクライアントが標準で無効なので、PowerShellの `Test-NetConnection サーバ名 -Port 80` が同じ用途に使えます。`TcpTestSucceeded : True` なら到達できています。
経路の確認は `tracert`、名前解決の確認は `nslookup` または `Resolve-DnsName`、自分のIP設定は `ipconfig /all` です。
:::

:::message
**2026年の注意点：Windows 10のサポート終了**
Windows 10は2025年10月にサポートが終了しました。病院では医療機器のコンソールや古い部門システムの端末にWindows 10（さらに古いOSも）が残っていることが多く、これらは**ネットワーク上で隔離する**必要があります（専用VLAN、通信先の制限、インターネット遮断）。トラブルシュートの前提として、「その端末はどのOSで、どのVLANにいるか」を台帳で把握しておきます。
:::

### pingの順番で問題箇所を絞る

「端末 → デフォルトゲートウェイ → その先のルータ → サーバ」の順にpingを打つと、どこで途切れるかで問題箇所が絞れます。

- ゲートウェイまで通らない：端末の設定（IP、マスク、ゲートウェイ）かケーブルかスイッチ
- ゲートウェイまで通るがその先が通らない：ルータの経路設定かフィルタ
- サーバまで通るのにアプリが動かない：サービス側（telnetでポート確認へ）

## 無線の申告別チェックリスト

| 申告 | 疑う原因 | 確認・対処 |
|---|---|---|
| つながらない / 遅い | 電波が届いていない（カバレッジホール） | 端末の位置でシグナルを確認。APの出力調整、APの増設 |
| 遅い | 電波干渉（意図しないAP、持ち込みのモバイルルータ、電子レンジ） | 干渉源を特定し、チャネルを変えるか干渉源を排除 |
| つながらない | SSID・パスワード・認証方式の不一致、証明書の期限切れ | 端末側の設定を確認。証明書の有効期限も確認 |
| つながるが遅い | ピンポン（頻繁に切り替わる）／スティッキー（遠いAPを掴んだまま） | `netsh wlan show interfaces` で接続先BSSIDとシグナルを確認。APの出力調整、端末の無線ドライバで「ローミングの積極性」を調整 |
| 切れる（不定期） | DFSによるチャネル変更に端末が追従できない | W52だけを使う設計に変更、または端末を更新 |
| 切れる（放置後） | 端末の省電力モードで無線が切られる | 電源オプションと無線アダプタの省電力設定を変更 |
| 昨日までつながっていたのに今日つながらない | ランダムMACアドレスが変わった（MAC認証環境） | 端末のランダムMACアドレスをオフにする |

:::message
**tips：「遅い」の切り分けは、まず"どのAPに"つながっているかを見る**
電波強度、DFS、ピンポン/スティッキーのどれも、`netsh wlan show interfaces` の結果（BSSID・チャネル・シグナル・無線の種類）から入れます。同じ場所で数回実行して、BSSIDがころころ変わるならピンポン、遠いAPのBSSIDのままならスティッキーです。
:::

:::message
**tips：省電力設定は「置きっぱなし端末」で頻発する**
ナースステーションのノートPCなど、操作間隔が空く端末で「気づいたら切れている」はほぼこれです。Windowsなら、電源オプション → ワイヤレスアダプターの設定 → 「最大パフォーマンス」、およびデバイスマネージャーの無線アダプター → 電源の管理 → 「電力の節約のためにオフにする」のチェックを外します。管理ツールで一括配布しておくと再発しません。
:::

## よくある人的ミスと教訓

ネットワーク障害の多くは、機器の故障ではなく人の作業が引き金です。典型的なパターンと教訓をまとめます。

### DNSサーバのIPアドレスが予告なく変更された

- 原因：作業影響の確認不足
- 教訓：WindowsドメインではドメインコントローラがDNSを兼ねているので、DNSの変更は「全端末に影響する作業」として扱う。ドメインコントローラを冗長化しておけば影響は軽微で済む。統合監視があれば早期に検知できる

### サーバのIPアドレスが予定作業で重複した

- 原因：新しいサーバに、既存機器が使っているIPを割り当てた
- 症状：すぐには気づきにくく、「ときどきつながらない」という分かりにくい症状になる
- 教訓：**pingを流し続けながら作業する**、**ARP表を確認しながら作業する**。台帳（第1章）が正しければ起きない

### サーバ室内でLANケーブルがループされた

- 原因：抜けているケーブルを親切心で挿した、配線整理中に誤って挿した
- 教訓：ループ検知・ストーム制御（第1章）を入れ、トラップ通知ですぐ気づけるようにする。空きポートは無効化しておく

### 通信フィルタを調整したら機器にログインできなくなった

- 原因：手順のミスで、自分の管理端末からの通信まで止めた
- 教訓：遠隔で機器のフィルタを変えるときは、**まず「管理端末からの通信を許可する行」を先頭に入れてから**他を変える。可能なら「○分後に自動で元に戻す」設定をしてから作業する

### 無線コントローラのフェイルオーバーで全断

- 原因：設計ミス。導入時に障害試験をしていなかった
- 教訓：**障害試験は導入時に実施して、報告書をもらう**。冗長化は「設定してある」ではなく「片方を止めても動いた」ことを確認して初めて完成

### 物理ポートの「半落ち」

- 状況：サーバスイッチの光モジュールが壊れかけて、片方向だけ通信できる状態になり、壊れたパケットで院内ネットワーク全体が不安定に
- 失敗：リンクランプの異常を見落とし、通信量のチェックから始めてしまった。実は落ちる直前に「UDLD異常」のSNMPトラップが1回出ていた
- 復旧：該当ポートのケーブルを抜いて復旧
- 教訓：**落ち際の1通のトラップ**が糸口になる。トラップは必ず外部に保存し、障害時は「直前に何か通知が来ていないか」を最初に見る

:::message
**用語メモ：UDLD**
UDLD（UniDirectional Link Detection）は「片方向しか通じていない回線」を検知する機能です。光ファイバは送りと受けが別々の線なので、片方だけ壊れる「半落ち」が起きます。この状態はリンクランプが点いたままなので、目視では気づきにくいのが厄介な点です。光回線を使う幹線では、UDLDや同等の機能を有効にしておきます。
:::

## 作業前チェックリスト

人的ミスの教訓をまとめると、作業前に次を確認する習慣になります。

- □ 影響範囲を台帳で確認した（この機器・このアドレスに依存しているものは何か）
- □ 作業中に監視するping／ログを開いた
- □ 元に戻す手順（ロールバック）を用意した
- □ 遠隔作業なら、自分を締め出さない設定を先に入れた
- □ 作業後に確認する項目（誰が・何を・どう確認するか）を決めた
- □ 関係部署に作業時間と影響を連絡した
